# Deployment Guide (source install)

This guide is written for an **agent (and humans) who want to deploy purplemux
from source** — the "always editable" deployment mode. It reflects how
purplemux is actually run on the reference Kali host (hostname `kali`,
`192.168.99.4`, user `a9017`) where Pi and omp agents are integrated.

If you are only consuming a stable build, prefer a packaged artifact instead of
this guide.

---

## 1. Architecture (what actually runs)

| Component | Path (after build) | Responsibility |
|---|---|---|
| Server entrypoint | `dist/server.js` | Own WebSocket/Timeline/TUI/status servers, proxies to Next standalone |
| Frontend server | `.next/standalone/server.js` | Next.js production server (traced deps, `require`d by `dist/server.js`) |
| Static assets | `.next/standalone/public`, `.next/standalone/.next/static` | Copied there by `scripts/post-build.js` |
| Web UI | served on `http://HOST:PORT` (default `8022`) | The purplemux dashboard |
| Agent sessions | `~/.pi/agent/sessions` / `~/.omp/agent/sessions` | Pi and omp jsonl session files |
| Extensions | `~/.purplemux/pi-extension.ts`, `~/.purplemux/omp-extension.ts` | Loaded by agents via `--extension` (autogenerated launch commands) |
| Runtime state | `~/.purplemux/` (`cli-token`, `port`, `logs/`) | CLI-token, port file, pino JSON logs |

```
browser ─▶ purplemux (dist/server.js, port 8022) ─▶ tmux -L purple (pt-ws-* sessions)
              │                                          │
              └── ◀ hooks ◀── pi/omp --extension (send session/agent events)
```

The reference host runs the service as a **systemd *user*** service :

```ini
# ~/.config/systemd/user/purplemux-8022.service
[Service]
Type=simple
WorkingDirectory=/home/a9017/purplemux/source
Environment=HOME=/home/a9017
Environment=USER=a9017
Environment=LOGNAME=a9017
Environment=SHELL=/usr/bin/zsh
Environment=PATH=/home/a9017/.local/bin:/home/a9017/.bun/bin:/usr/local/bin:/usr/bin:/bin
Environment=NODE_ENV=production
Environment=PORT=8022
Environment=HOST=0.0.0.0
Environment=PURPLEMUX_HEARTBEAT_TIMEOUT_MS=86400000
ExecStart=/usr/bin/node /home/a9017/purplemux/source/dist/server.js
Restart=always
RestartSec=3
TimeoutStopSec=15
KillMode=control-group
```

## 2. Requirements

- **Node.js >= 20** (the reference host also uses `pnpm`; `pnpm` is used to
  install dependencies. `npx`/`npm` work if `pnpm-lock.yaml` handling is
  consistent, but prefer pnpm for the lockfile).
- **tmux** (all agent terminals run inside tmux; the tmux socket used at
  runtime is `-L purple`, so sessions are named `pt-ws-<ws>-pane-<pane>-tab-<tab>`).
- **A Linux/macOS host** (works on Kali Debian; Node native compile for
  `node-pty` happens on install).
- **systemd (user)** is recommended but any process supervisor that keeps the
  server alive works.

---

## 3. First-time deployment (the whole flow, in order)

```bash
# 1) Clone (this host uses ssh to github:9018/purplemux)
git clone git@github.com:9018/purplemux.git
cd purplemux

# 2) Install dependencies (native module node-pty compiles here;
#    postinstall chmod's its spawn-helper)
pnpm install

# 3) Build the whole app:  next build → post-build.js → tsup
pnpm build

# 4) Runtime dir (token, logs, extensions)
mkdir -p ~/.purplemux
#   - cli-token:  a random token used as header `x-pmux-token`
#   - port file:  used by the extensions to know where to POST hooks
#   Copy or generate; the server reads them at boot. The CLI token can be
#   regenerated at any time; clients must use the same one.

# 5) Install the user service — create `~/.config/systemd/user/purplemux-8022.service`
   using the template from section 1 (adjust `WorkingDirectory`/`ExecStart`):
systemctl --user daemon-reload
systemctl --user enable --now purplemux-8022
sleep 4
systemctl --user is-active purplemux-8022   # → active

# 6) Health check
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8022/login   # → 200
```

If you don't use systemd, `NODE_ENV=production node dist/server.js` from the
repo root is the equivalent of `ExecStart`.

## 4. Daily iteration loop (the reason you chose this flow)

```bash
# after editing TS files:
pnpm build                       # or `npx tsup --watch` for server-only changes
systemctl --user restart purplemux-8022
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8022/login   # 200
```

### ⚠️ Build chain specifics (CRITICAL)

`pnpm build` runs **three** steps, in this order:

1. `next build` — frontend → `.next/` (this includes the standalone server;
   `next.config` sets `output: "standalone"`).
2. `node scripts/post-build.js` — copies `public/` and `.next/static` into
   `.next/standalone/` and strips env files.
3. `tsup` — bundles `src/server.ts` → `dist/server.js` (`tsup.config.ts` has
   **`clean: true`**, i.e. it **deletes `dist/` first**!).

> **Never run `tsup` alone with a failing compile.** If `tsup` fails, `dist/`
> is empty and the running server (which loads `dist/server.js` from disk) will
> crash on next restart. Rule: **make sure TypeScript compiles (`npx tsc --noEmit`)
> before running `tsup`, and only restart the service after `tsup` produced a
> fresh `dist/server.js`** (check `mtime` vs your edit time).

### Auto-reload of agent extension changes does NOT exist

Agents (`pi`, `omp`) load `~/.purplemux/*.extension.ts` **at process start**.
After editing an extension, restart the agent process in the tmux tab (the
panel's "new session" / resume buttons restart with the new file).

## 5. Auth & checks (used by the dashboard & extensions)

- Dashboard UI login password is set via config (the CLI user knows it; the
  stored form is an scrypt hash, not reversible).
- API hook auth: header `x-pmux-token: <token from ~/.purplemux/cli-token>`.
- WebSocket auth (`/api/timeline`, `/api/status`) uses a **session cookie**;
  obtain one:

```bash
rm -f /tmp/pm-cookie.txt
curl -c /tmp/pm-cookie.txt -H 'Content-Type: application/json' \
     -d '{"password":"1234"}' http://127.0.0.1:8022/api/auth/login
```

Then a timeline ws test:

```bash
node /tmp/wsinit2.mjs <sessionId> <hint-session-id> pi   # example; reads cookie
```

Debug endpoints (with cookie): `/api/timeline?...`  returns the current
timeline for a tab, `/api/status` is a WS that pushes tab state
(`status:sync` includes `cliState`, `agentSessionId`, `jsonlPath`).

## 6. Agent session detection (how the chat panel follows the working agent)

Order of resolution per tab (most authoritative first):

1. **Explicit** `--session <id>` / `--resume <id>` in the spawned process
   cmdline (parsed by `src/lib/providers/session-detection.ts`).
2. **Hook metadata** — `session_start`, `session_before_switch` events posted
   by the agent extension (carrying the jsonl file path / session id).
3. **cwd heuristic** — recent session files under the process cwd, filtered by
   process start time window (start ±60s, upper bound +30s).
4. Empty (does not guess).

In-app resume (TUI `/resume`) fires `session_before_switch` with the **target
session file**; `dist/server.js` reads the session id from that file and
rebinds the tab, which makes the browser re-connect to the new session (the
front-end watches `agentSessionId` changes). TUI-only resumes with no
command-line switch are therefore supported as of v0.4.5.

## 7. Updating to a newer revision

```bash
git pull                          # get latest
pnpm install                      # in case deps changed
pnpm build                        # full chain (see warnings above)
systemctl --user restart purplemux-8022
# optional: bump LOG_LEVELS drop-in if you want quieter logs:
#   ~/.config/systemd/user/purplemux-8022.service.d/hooks-debug.conf
```

If you use a git worktree like the reference host (e.g. `source/`), the
service unit already points at it; keep `WorkingDirectory` in sync.

## 8. Diagnostics

| Symptom | Check |
|---|---|
| Service down / dist missing | `systemctl --user status purplemux-8022`; if `dist/` is empty, tsup wiped it after a failed compile — rebuild `dist/server.js` first. |
| Timeline empty for a tab | Put the tab into a login: `/api/timeline?...` returns `jsonlPath`; validate `~/.pi/agent/sessions/<id>.jsonl` exists. For a fresh start that rejects cwd guesses, `--session`/`--resume` args or a hook event are needed. |
| `session_start` hook shows null fields | These are startup broadcasts (previous to session file creation) — expected. True `resume` shows as `session_before_switch` with `targetSessionFile`. |
| `ps -o lstart` yields local/Chinese locale | Internal code reads `/proc/<pid>/stat` starttime + `/proc/stat` btime (CLK_TCK=100), independent of locale. Do not rely on `ps` parsing yourself. |
| Memory pressure | Reference host has 7.8GiB RAM + 3.1Gi swap; a full `pnpm build` plus several tmux/agent processes can OOM. Restart tmux-only panes, or raise swap. |
| WebSocket auth failures | Cookie missing/expired — re-login (`/api/auth/login`); ws uses session cookie, not the cli token. |

## 9. Layout maps & debugging endpoints

- `/api/layout` — serialized layout (tabs, panes) persisted under
  `~/.purplemux/layout.json`.
- `/api/status` (WS) — live tab state; `status:sync` snapshot.
- `/api/pi/launch-command`, `/api/omp/launch-command` — inspect the exact
  command the panel will run (shows `--extension`, `--cwd`, `--resume`).

---

## 10. Files you should NOT edit by hand

- `dist/*` — build artifacts, deleted by `tsup`.
- `.next/standalone/*` — build artifacts.
- `~/.purplemux/logs/*` — pino logs (JSON lines).

The single source of truth for "what is deployed" is `dist/server.js` +
`.next/standalone/server.js` — always rebuilt together via `pnpm build`.
